# Лабораторная работа: Git и передача проектов по SSH

## Перед началом

В работе используются рабочий стол **xrdp** и три Debian-узла: **Git1, Git2, Git3**.
Все команды ниже вводятся в терминале **на рабочем столе xrdp**.
Команды внутри кавычек после `ssh` выполняются на указанном удалённом узле.

На рабочем столе и на узлах должен быть установлен Git. SSH-псевдонимы
`Git1`, `Git2`, `Git3` должны подключать вас к соответствующим узлам под
пользователем `root`. Настройте имена узлов, SSH-конфигурацию и ключи по
заданию преподавателя. Сетевая подготовка этого за вас не делает.

Проверьте доступ:

```sh
ssh Git1 'id -un'
ssh Git2 'id -un'
ssh Git3 'id -un'
```

`id -un` выводит имя пользователя. На каждом узле ожидается `root`.
При первом подключении SSH может попросить подтвердить ключ сервера:
сверьте его с данными преподавателя и подтвердите подключение.

Исходный файл `git-lab-source.bundle`, полученный от преподавателя,
сохраните в домашнем каталоге пользователя рабочего стола xrdp.
Bundle — файл с Git-репозиторием и его историей; из него можно сделать клон
так же, как из сетевого репозитория. Отдельный Git-сервис для работы не нужен.

Исходный проект содержит:

- `README.md` — описание проекта;
- `lab.conf` — название лаборатории и ответственный;
- `services.txt` — перечень сервисов;
- ветку `main` — исходную версию;
- ветку `training` — версию с названием «Тренировочная лаборатория».

Тегов в исходном проекте нет. Запускать проект как программу не требуется.

**Каждое из пяти заданий нужно выполнить на всех трёх узлах.** Результаты
хранятся в `/root/task-01` … `/root/task-05`. Сохраняйте все эти каталоги до
окончательной проверки. На xrdp домашний каталог принадлежит вашему
пользователю и не обязательно находится в `/root`.

### Как читать команды

- `~` — домашний каталог пользователя той машины, где выполняется команда.
- `git -C ~/task-01 ...` — выполнить действие Git в указанном каталоге,
  не меняя текущий каталог терминала.
- `ssh Git1 'команда'` — выполнить команду на Git1. Одинарные кавычки
  сохраняют `~` для обработки удалённой оболочкой: там это `/root`.
- `Git1:task-01` — адрес Git по SSH: узел Git1 и каталог `task-01`
  относительно домашнего каталога удалённого пользователя, то есть `/root/task-01`.

Команды `clone` и начальный `init` в инструкции рассчитаны на новые каталоги.
Если каталог уже существует, сначала посмотрите его содержимое и состояние:
не удаляйте выполненную работу ради повторного запуска инструкции.

## Задание 1. Передать исходный проект на три узла

**Цель:** разместить исходную ветку `main` в `/root/task-01` на каждом узле.
Собственные изменения не требуются.

### 1. Получить копию на xrdp

```sh
cd ~
git clone --branch main ~/git-lab-source.bundle ~/task-01
```

`cd` меняет текущий каталог. `clone` создаёт обычный рабочий репозиторий,
а `--branch main` выбирает начальную ветку. В `task-01` появятся файлы проекта
и скрытый каталог `.git`, хранящий историю и настройки Git.

Посмотрите ветки:

```sh
git -C ~/task-01 branch
git -C ~/task-01 branch -a
```

Первая команда показывает локальные ветки: ожидается `* main`.
Звёздочка отмечает выбранную ветку. `-a` дополнительно показывает ссылки
на ветки источника, например `remotes/origin/training`. Это не локальные ветки.

### 2. Создать принимающий репозиторий

```sh
ssh Git1 'git init --initial-branch=main ~/task-01'
ssh Git1 'git -C ~/task-01 config receive.denyCurrentBranch updateInstead'
```

`init` создаёт пустой обычный репозиторий на Git1. В нём будут и история,
и рабочие файлы. `--initial-branch=main` задаёт имя начальной ветки.

`config` сохраняет настройку этого репозитория. Значение `updateInstead`
разрешает принимать отправку в выбранную ветку и обновлять рабочие файлы,
если принимающий рабочий каталог и индекс чистые. Без этой настройки Git
обычно запрещает такую отправку в обычный репозиторий.

Повторите создание и настройку на остальных узлах:

```sh
ssh Git2 'git init --initial-branch=main ~/task-01'
ssh Git2 'git -C ~/task-01 config receive.denyCurrentBranch updateInstead'
ssh Git3 'git init --initial-branch=main ~/task-01'
ssh Git3 'git -C ~/task-01 config receive.denyCurrentBranch updateInstead'
```

### 3. Передать main

```sh
git -C ~/task-01 push Git1:task-01 main
git -C ~/task-01 push Git2:task-01 main
git -C ~/task-01 push Git3:task-01 main
```

`push` передаёт сохранённую историю. После адреса указанa отправляемая
ветка `main`. Каждый узел обновляется отдельно: отправка на Git1
не обновляет Git2 и Git3. Ветку `training` в этом задании не отправляйте.

### 4. Проверить результат

```sh
ssh Git1 'git -C ~/task-01 --no-pager log --oneline main'
ssh Git1 'git -C ~/task-01 status'
ssh Git1 'git -C ~/task-01 branch'
```

`log` показывает историю, `--oneline` сокращает каждый коммит до одной строки,
`--no-pager` выводит результат без отдельного просмотрщика. Коммит —
сохранённая версия проекта с собственным идентификатором и описанием.
`status` показывает выбранную ветку и несохранённые изменения.

Повторите проверки для Git2 и Git3, заменяя имя после `ssh`.

**Для сдачи на каждом узле:** обычный репозиторий `/root/task-01`, выбрана
единственная локальная ветка `main`, её история и последний коммит точно
совпадают с исходной `main`. Файлы и индекс чистые, тегов нет,
`receive.denyCurrentBranch=updateInstead`.

## Задание 2. Посмотреть файлы и историю

**Цель:** создать отдельный репозиторий `/root/task-02` на каждом узле
и научиться читать его содержимое и состояние.

### 1. Получить новую копию

```sh
git clone --branch main ~/git-lab-source.bundle ~/task-02
```

Это новая независимая рабочая копия исходного проекта. `task-01` сохраняется.

### 2. Подготовить узлы и передать проект

Далее для одинаковых действий на трёх узлах используется цикл оболочки:

```sh
for node in Git1 Git2 Git3; do
    ssh "$node" 'git init --initial-branch=main ~/task-02'
    ssh "$node" 'git -C ~/task-02 config receive.denyCurrentBranch updateInstead'
    git -C ~/task-02 push "$node":task-02 main
done
```

`for` по очереди присваивает переменной `node` значения Git1, Git2 и Git3.
Команды между `do` и `done` выполняются для каждого значения.
`"$node"` подставляет текущее имя узла. Это сокращённая запись тех же
отдельных команд, которые использовались в задании 1.
Если одна из команд завершилась ошибкой, исправьте её: цикл сам по себе
не подтверждает успешное выполнение всех действий.

### 3. Изучить результат на узле

```sh
ssh Git1 'ls -a ~/task-02'
ssh Git1 'cat ~/task-02/README.md'
ssh Git1 'cat ~/task-02/lab.conf'
ssh Git1 'git -C ~/task-02 --no-pager log --oneline main'
ssh Git1 'git -C ~/task-02 status'
```

`ls` выводит содержимое каталога, `-a` включает скрытые файлы и `.git`.
`cat` читает файл. Файлы проекта уже находятся в рабочем каталоге:
создавать рядом ещё один клон на узле не требуется.

Ожидается выбранная `main` и сообщение о чистом рабочем каталоге.
Повторите эти команды для Git2 и Git3.

**Для сдачи на каждом узле:** `/root/task-02` содержит исходную `main`
и исходные файлы. Выбрана единственная локальная ветка `main`, рабочий
каталог и индекс чистые, тегов нет, `receive.denyCurrentBranch=updateInstead`.
Просмотр файлов и истории нужен для обучения; автопроверка оценивает
сохранённое состояние репозитория.

## Задание 3. Изменить настройку и сохранить версию

**Цель:** создать один собственный коммит и передать одинаковую историю
на все три узла в `/root/task-03`.

### 1. Получить новую копию и настроить автора

```sh
git clone --branch main ~/git-lab-source.bundle ~/task-03
git -C ~/task-03 config user.name 'Lab User'
git -C ~/task-03 config user.email 'student@example.invalid'
```

`user.name` и `user.email` — подпись автора будущего коммита.
Это не логин и пароль для SSH. Эти настройки действуют в данном репозитории.
Можно использовать собственные имя и адрес: автопроверка их не фиксирует.

### 2. Изменить одну строку

В текстовом редакторе **на xrdp** откройте `~/task-03/lab.conf`.
Замените только строку:

```text
MAINTAINER="Не назначен"
```

на:

```text
MAINTAINER="Учебная группа"
```

Сохраните файл. Остальные строки и файлы не меняйте.

### 3. Посмотреть и подготовить изменение

```sh
git -C ~/task-03 --no-pager diff
git -C ~/task-03 add lab.conf
git -C ~/task-03 --no-pager diff --staged
```

`diff` показывает изменения рабочего файла относительно индекса.
Строка с `-` — прежнее значение, с `+` — новое.
`add` помещает изменение в индекс — набор изменений для будущего коммита.
`diff --staged` показывает подготовленное изменение относительно последнего
коммита. На обоих этапах ожидается замена только одной строки.

### 4. Создать один коммит

```sh
git -C ~/task-03 commit -m 'Указать ответственного'
git -C ~/task-03 status
```

`commit` сохраняет подготовленное изменение в локальной истории.
`-m` задаёт сообщение; его можно выбрать самостоятельно.
Коммит пока существует только в копии на xrdp. После него ожидается чистый
рабочий каталог.

Нужен **ровно один новый коммит непосредственно после исходной main**.
Если заметили ошибку до отправки, исправьте файл, выполните `git add lab.conf`
и `git commit --amend --no-edit`: это заменит последний собственный коммит,
сохранив его сообщение. Не создавайте второй коммит для исправления этой работы.

### 5. Передать результат на три узла

```sh
for node in Git1 Git2 Git3; do
    ssh "$node" 'git init --initial-branch=main ~/task-03'
    ssh "$node" 'git -C ~/task-03 config receive.denyCurrentBranch updateInstead'
    git -C ~/task-03 push "$node":task-03 main
done
```

Передаётся одна и та же история с xrdp. Не создавайте аналогичные коммиты
отдельно на узлах: даже при одинаковых файлах идентификаторы могут отличаться.

### 6. Сравнить идентификаторы

```sh
git -C ~/task-03 rev-parse main
for node in Git1 Git2 Git3; do
    ssh "$node" 'git -C ~/task-03 rev-parse main'
done
```

`rev-parse main` выводит полный идентификатор последнего коммита ветки.
Все четыре строки должны совпадать. Сохраните локальную копию `task-03`
для следующего задания.

**Для сдачи на каждом узле:** выбрана единственная локальная ветка `main`;
один новый коммит меняет только значение `MAINTAINER` на `Учебная группа`.
Остальные файлы сохранены. Хеш последнего коммита одинаковый на всех узлах.
Рабочий каталог и индекс чистые, тегов нет,
`receive.denyCurrentBranch=updateInstead`.

## Задание 4. Перенести собственную историю

**Цель:** разместить сохранённую историю задания 3 в новых репозиториях
`/root/task-04` на всех трёх узлах. Новых коммитов не требуется.

### 1. Скопировать выполненную работу

На xrdp:

```sh
git clone --branch main ~/task-03 ~/task-04
git -C ~/task-03 rev-parse main
git -C ~/task-04 rev-parse main
```

Источником `clone` может быть локальный репозиторий. Новый клон получает
его сохранённую историю и рабочие файлы. Два выведенных идентификатора
должны совпадать.

Не клонируйте исходный bundle для этого шага и не повторяйте изменение
`MAINTAINER` новым коммитом: требуется перенести уже существующий коммит.

### 2. Подготовить новые места сдачи и передать main

```sh
for node in Git1 Git2 Git3; do
    ssh "$node" 'git init --initial-branch=main ~/task-04'
    ssh "$node" 'git -C ~/task-04 config receive.denyCurrentBranch updateInstead'
    git -C ~/task-04 push "$node":task-04 main
done
```

Меняется каталог назначения; репозитории `task-03` сохраняются.

### 3. Проверить историю и состояние

```sh
for node in Git1 Git2 Git3; do
    ssh "$node" 'git -C ~/task-03 rev-parse main'
    ssh "$node" 'git -C ~/task-04 rev-parse main'
    ssh "$node" 'git -C ~/task-04 status'
done
```

Все шесть идентификаторов должны совпасть. В `task-04` ожидается выбранная
`main` и чистый рабочий каталог.

**Для сдачи:** во всех шести репозиториях `task-03` и `task-04` последний
коммит `main` одинаковый. В `task-04` единственная локальная ветка — `main`,
она выбрана. Файлы и индекс чистые, тегов нет,
`receive.denyCurrentBranch=updateInstead`.
Оба задания проверяются в их текущем состоянии, поэтому сохраняйте
`task-03` и `task-04` без дальнейших изменений до окончательной проверки.

## Задание 5. Передать две ветки и выбрать training

**Цель:** разместить исходные ветки `main` и `training` в `/root/task-05`
на всех узлах и выбрать на каждом узле `training`.
Создавать собственные коммиты или объединять ветки не требуется.

### 1. Получить новый клон

```sh
git clone --branch main ~/git-lab-source.bundle ~/task-05
git -C ~/task-05 branch -a
cat ~/task-05/lab.conf
```

Сначала выбрана локальная `main`. В списке также видна `origin/training` —
ссылка на ветку источника. В файле ожидается исходное название лаборатории.

### 2. Создать локальную training и посмотреть её файлы

```sh
git -C ~/task-05 switch -c training --track origin/training
cat ~/task-05/lab.conf
```

`switch` переключает ветку; `-c training` создаёт локальную ветку,
`--track origin/training` связывает её с веткой источника.
Рабочие файлы обновляются автоматически. В `lab.conf` теперь ожидается:

```text
LAB_NAME="Тренировочная лаборатория"
MAINTAINER="Не назначен"
```

Ветка `main` при этом сохраняется. Второй каталог для другой ветки не нужен.
Если локальная `training` уже создана, для повторного переключения используйте
`git -C ~/task-05 switch training` без `-c`.

### 3. Сравнить версии и вернуться к main

```sh
git -C ~/task-05 --no-pager diff main training -- lab.conf
git -C ~/task-05 switch main
```

`diff main training` сравнивает две версии. `--` отделяет имена веток от
пути файла. Ожидается только различие названий лаборатории.
`switch main` возвращает рабочие файлы к `main`, не удаляя `training`.

### 4. Создать репозитории и передать обе ветки

```sh
for node in Git1 Git2 Git3; do
    ssh "$node" 'git init --initial-branch=main ~/task-05'
    ssh "$node" 'git -C ~/task-05 config receive.denyCurrentBranch updateInstead'
    git -C ~/task-05 push "$node":task-05 main training
done
```

После адреса перечислены две отправляемые ветки. Их передача не объединяет
изменения: обе версии остаются отдельными ветками.

### 5. Выбрать training на каждом узле

```sh
for node in Git1 Git2 Git3; do
    ssh "$node" 'git -C ~/task-05 switch training'
    ssh "$node" 'git -C ~/task-05 status'
    ssh "$node" 'cat ~/task-05/lab.conf'
done
```

Переключение на xrdp не переключает ветки на удалённых узлах автоматически.
Поэтому `switch training` выполняется отдельно на каждом узле через SSH.

**Для сдачи на каждом узле:** ровно две локальные ветки — `main` и `training`,
обе указывают на соответствующие исходные коммиты из бандла. Выбрана `training`,
рабочие файлы точно соответствуют ей. Новых коммитов и тегов нет,
рабочий каталог и индекс чистые, `receive.denyCurrentBranch=updateInstead`.
Ссылки на ветки источника вида `origin/main` допускаются.

## Итоговая проверка перед сдачей

На **каждом** из Git1, Git2, Git3 должны сохраниться все пять репозиториев:

| Каталог | Выбранная ветка | Ожидаемый результат |
| --- | --- | --- |
| `/root/task-01` | `main` | Исходная main без изменений |
| `/root/task-02` | `main` | Исходная main без изменений |
| `/root/task-03` | `main` | Один коммит с изменением MAINTAINER |
| `/root/task-04` | `main` | Точный коммит из task-03 |
| `/root/task-05` | `training` | Исходные main и training, выбрана training |

Во всех репозиториях должны быть чистые рабочие каталоги и индексы.
Проверить это можно командой `git status --porcelain`: пустой вывод означает,
что Git не обнаружил подготовленных, неподготовленных или неотслеживаемых
изменений. Обычный `git status` даёт более подробное пояснение.

## Где здесь появился бы PR

В этих заданиях используются Git и SSH. Создавать настоящий PR не требуется:
на лабораторных узлах нет платформы ревью.

Если бы изменение из `training` требовалось принять в `main` через Gitea,
следующим действием было бы создание PR из `training` в `main` с просмотром
разницы и обсуждением. Отправка ветки, создание PR и объединение веток —
три разных действия. Успешный `push training` не включает её изменения в `main`.
